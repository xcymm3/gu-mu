# 《血蛊引》视觉小说产品与界面规格

> 状态：第一步基线，2026-08-22 冻结。  
> 适用范围：主菜单、角色选择、剧情阅读、选项、战斗、存读档、历史、设置与结局一览。  
> 目标：将当前 Next.js 游戏逐步改造为桌面端优先的完整网页视觉小说，同时保留既有剧情、战斗数值、存档和结局规则。

## 1. 文档权威与改动原则

本文是视觉表现和交互行为的权威合同。后续 Agent 实现界面时必须遵守本文；剧情事实仍以 `lib/xue-gu-yin/story/data.ts`、`docs/story-flow.md` 和测试为准，`lib/xue-gu-yin/game.ts` 保留为状态运行时与兼容门面。

规则冲突时按以下优先级处理：

1. 自动测试与战斗共享结算规则；
2. 本文的舞台、排版、交互和无障碍合同；
3. `docs/AI-AGENT-STORY-GUIDE.md` 的五幕与剧情维护合同；
4. 具体页面当前实现。

本阶段只冻结规范，不要求一次性重写现有界面。后续改造应渐进进行，禁止为了视觉重构删除剧情、战斗、存档或结局功能。

## 2. 产品定位

### 2.1 目标用户

- 主要用户是熟悉日式视觉小说操作习惯的桌面端玩家。
- 玩家关注剧情推进、角色关系、路线选择、结局收集和稳定的存读档。
- 玩家应当可以长时间阅读，不需要理解网页布局或寻找下一步按钮。

### 2.2 核心体验

玩家进入游戏后的主要循环必须始终清晰：

```text
观看场景与角色
→ 阅读一段对白或旁白
→ 推进到下一段
→ 在关键处作出选择或进入战斗
→ 状态被记录
→ 继续阅读或进入结局
```

在标准剧情界面中，唯一的主操作是“推进文本”。保存、读取、历史、自动播放等功能是辅助操作，不能抢夺视觉重心。

### 2.3 风格定位

- 类型：桌面端视觉小说，而不是文章阅读器、手游卡片页或管理后台。
- 基调：阴冷、克制、诡谲；血色仅用于危险、蛊术和剧情异变。
- 构图：场景先于界面，人物先于装饰，对话框压在画面下缘。
- 参考目标是《千恋＊万花》《魔女的夜宴》的阅读节奏、角色演出和功能完整度，不复制其美术、字体、布局像素或声音资源。
- 不采用玻璃拟态、霓虹渐变、卡片套卡片、悬浮数据看板等通用网页风格。

## 3. 不可破坏的产品合同

### 3.1 五幕结构

```text
第一幕：1 个剧情节点
第二幕：6 个剧情节点
第三幕：每条路线 4 个剧情节点
第四幕：每条路线 6 个剧情节点
第五幕：每条路线 2 个剧情节点
```

节点数量是剧情结构合同，不等于屏幕页数。第三幕起四条路线完全独立，不再使用公共高潮。一个节点内部可以包含任意数量的对白、旁白、角色动作、背景变化、选项和战斗事件。

### 3.2 内容与逻辑保留

- 三种主角身份、隐藏关系、旗标、路线和结局条件保持不变，除非用户明确要求修改剧情设计。
- 战斗运行时与测试必须继续调用 `lib/xue-gu-yin/combat.ts` 的共享纯函数。
- 敌人生命仍只显示“健康／受伤／重伤”，不得在视觉层暴露具体数值。
- 游方蛊医不能击败苏衍，但结局一览使用全局统一图鉴，仍会展示对应真结局槽位；身份差异只影响实际可达性。
- 页面重构不能改变既有存档含义；更改状态结构时必须提升存档版本并提供迁移。

### 3.3 禁止事项

- 禁止让剧情页依赖浏览器页面滚动。
- 禁止让标准对白框出现滚动条。
- 禁止通过缩小到不可读字号来塞入长文本。
- 禁止在 React 组件中重新硬编码剧情、路线或结局判断。
- 禁止依靠鼠标悬停才能看到必要信息。
- 禁止使用未经授权的商业游戏素材作为占位图。

## 4. 舞台与视口合同

### 4.1 基准坐标

| 项目 | 规格 |
| --- | --- |
| 设计坐标 | `1920 × 1080` |
| 舞台比例 | `16:9` |
| 桌面基线 | `1280 × 720` |
| 推荐体验 | `1366 × 768` 及以上 |
| 宽屏处理 | 居中显示 16:9 舞台，外围使用主题化留边 |
| 窄屏处理 | 缩放舞台并启用紧凑布局，不裁掉交互区 |
| 页面滚动 | 游戏运行时禁止 |

实现时以一个 `aspect-ratio: 16 / 9` 的舞台为坐标容器。所有背景、立绘、对话框和演出层相对舞台定位；窗口只负责缩放和留边，不允许分别拉伸横纵方向。

### 4.2 桌面布局安全区

基于 `1920 × 1080` 设计坐标：

- 四周视觉安全边距：至少 `48`。
- 关键文字与按钮安全边距：至少 `72`。
- 对话框建议范围：横向 `120–1800`，纵向 `748–1010`。
- 人物立绘底部可以延伸到舞台外，但脸部与关键动作不得进入顶部 `72` 或两侧 `48` 的裁切风险区。
- 快捷菜单固定在对话框下缘或内部底缘，不额外挤压正文高度。

### 4.3 小窗口与移动兼容

桌面端是主要目标，但小屏不得不可用：

- 在 `960px` 以下进入紧凑模式，减少装饰与同时出现的角色数量。
- 在 `640px` 以下可采用竖向重新排版，不强制用户横屏。
- `320px`、`375px`、`414px`、`768px` 宽度不得产生横向滚动或按钮出界。
- 小屏可以缩短快捷菜单标签，但不能隐藏“推进、菜单、保存、读取”四项核心能力。
- 小屏仍禁止对白框滚动；由分页器生成更多页。

## 5. 舞台分层

所有视觉小说场景使用同一套语义层，不得由具体剧情自由发明 `z-index`：

| 层级 | 名称 | 职责 |
| ---: | --- | --- |
| 1 | `stage-background` | 背景图、天气底图 |
| 10 | `stage-atmosphere` | 雾、雨、暗角、静态光影 |
| 20 | `stage-characters` | 左／中／右立绘 |
| 30 | `stage-effects` | 受击、闪白、血色遮罩、粒子 |
| 40 | `stage-dialogue` | 人名框、对白框、旁白框 |
| 50 | `stage-choices` | 选项覆盖层 |
| 60 | `stage-quick-menu` | 快捷菜单、自动／快进状态 |
| 80 | `stage-overlay` | 历史、保存、读取、设置 |
| 90 | `stage-modal` | 确认、错误和阻断提示 |
| 100 | `stage-loading` | 启动与资源加载遮罩 |

背景、角色、特效和界面必须是独立层。换立绘表情不得重新加载背景；打开菜单不得销毁当前剧情舞台。

## 6. 核心界面状态

### 6.1 主菜单

必须提供：

- 开始游戏；
- 继续游戏；
- 读取存档；
- 结局一览；
- 游戏设置。

主菜单采用一张主视觉背景加单列文字菜单。禁止首页使用多个等宽功能卡片。没有存档时“继续游戏”显示禁用状态，不从布局中消失。

### 6.2 身份选择

- 同屏展示三种身份，但以角色概念、能力倾向和专属蛊区分，不展示隐藏关系或路线答案。
- 身份卡允许使用人物剪影或纹章，不强制绘制主角脸部。
- 选中后必须有二次明确反馈，但不使用阻断式浏览器确认框。

### 6.3 标准剧情

- 背景铺满舞台。
- 最多同时突出三名角色，当前说话者最亮。
- 对话框位于舞台下方，保留背景和角色面部可见区域。
- 单击舞台空白区、对白框或使用键盘均可推进。
- 快捷菜单视觉权重低于正文与人物名。

### 6.4 旁白

旁白不显示人物名。可使用以下两种模式：

1. 底部旁白框：普通场景描述；
2. 中央叙事层：章节开场、时间跳转或重大死亡。

中央叙事层不得与角色对白同时出现。

### 6.5 选择

- 选择层出现时暂停自动播放和快进。
- 选项位于画面中部偏上，避免遮住底部对话框的上下文。
- 单屏建议 `2–4` 项，硬上限 `5` 项。
- 桌面端选项标签必须保持单行，建议不超过 `28` 个汉字；更长说明应在选择前的正文中交代。
- 选项不得显示隐藏属性阈值、关系数值或“正确答案”提示。

### 6.6 战斗

- 战斗接管完整舞台，不在剧情正文下方嵌入卡片。
- 敌人位于中央或中上区域；玩家状态、敌方异动、回合反馈和蛊术选择各有固定区域。
- 反馈顺序必须是“玩家动作 → 敌人受击或特殊反应 → 敌方异动 → 下一次输入”。
- 战斗结果由共享结算器提供，视觉层只负责演出。
- 赵黎血幕反弹等特殊机制必须通过画面和文字明确说明死因，但预告仍保持叙事化。

### 6.7 历史、存读档和设置

- 这些是覆盖层，不跳转离开当前舞台。
- 打开时冻结文字推进、自动播放和战斗输入。
- 保存与读取采用分页存档位；不依赖整个页面滚动。
- 历史记录内容长度无上限，允许历史面板自身纵向滚动，这是游戏内唯一常规文本滚动区。
- 关闭覆盖层后，背景、立绘、当前字显进度和音乐位置保持不变。

### 6.8 结局

- 结局使用独立演出或 CG，不复用普通选择卡片。
- 明确显示结局名、短句、正文和“返回主菜单／从最近选择重试”。
- 解锁记录写入浏览器本地存储，并按主角身份过滤可达结局。

## 7. 对话框与自动分页合同

### 7.1 容量

在 `1920 × 1080` 设计坐标中：

- 人物对白正文：默认 `3` 行，最多 `4` 行；
- 底部旁白：默认 `4` 行；
- 中央叙事：最多 `6` 行；
- 每行建议 `28–36` 个汉字，最终以真实字体测量为准；
- 正文视觉字号约 `30–32` 设计像素，在 `1280 × 720` 下不得小于 `18px` CSS 像素。

### 7.2 分页规则

分页器必须遵守：

1. 字体加载完成后再测量；
2. 使用实际容器宽高和真实字体进行测量，不用固定字符数切割；
3. 优先按空段、句号、问号、叹号和引号闭合处分割；
4. 单句超长时才允许在逗号处分割；
5. 不把成对引号、姓名和紧随其后的冒号拆开；
6. 预留人名框、继续指示符和快捷菜单空间；
7. 窗口尺寸改变时重新分页，但同一尺寸下推进过程中页码不得抖动；
8. 选项只在该节点所有前置文本播放完毕后出现。

禁止用 `overflow-y: auto` 掩盖分页错误。文字装不下时必须增加页数。

### 7.3 文字渐显

- 默认按字符渐显，建议默认速度为每个汉字 `28ms`。
- 第一次推进：立即显示当前页全部文字。
- 当前页已完整显示后再次推进：进入下一页或下一事件。
- 标点可附加轻微停顿，但单次不得让玩家误以为游戏卡死。
- 屏幕阅读器读取完整句子，不逐字触发 `aria-live`。

## 8. 排版合同

### 8.1 字体角色

正式版本最多使用三套字体角色：

- `--font-display`：标题、人物名、章节名；优先选择有授权的中文宋体或现代明朝体。
- `--font-body`：对白和旁白；必须为屏幕阅读优化的中文字体。
- `--font-ui`：按钮、状态和设置；使用清晰的无衬线字体。

现有 `STKaiti/KaiTi` 只能作为开发阶段展示字体，不能作为跨平台最终依赖。进入正式美术阶段时，应选取可随网页发布的字体并自托管或使用可靠 CDN。

### 8.2 字号和行距

- 正文在任何支持尺寸下不得低于 `16px`，桌面基线建议 `18–22px`。
- 中文对白行高建议 `1.55–1.7`。
- 标题行高 `1.08–1.25`。
- 正文不使用全大写、斜体、超宽字距或两端强制对齐。
- 人物名与正文至少相差一个清晰层级，可通过字体、字号或重量实现。
- 数值显示使用等宽数字，但不额外引入第四套字体。

### 8.3 强调标记

- 人物名由数据字段渲染，不在正文中手写粗体模拟人名框。
- 危险、蛊术觉醒和关键死亡可使用血红语义色。
- 单页红色强调不超过两处，避免全文“重点化”。
- 不使用渐变文字。

## 9. 色彩与主题

### 9.1 语义色

沿用现有 `tokens.css` 的 OKLCH 语义系统：

- 墨绿／冷青：世界观锚色、普通界面和焦点状态；
- 暖白／浅纸色：亮色对话框和正文承载面；
- 深墨色：暗色舞台、菜单遮罩和墓穴氛围；
- 血红：危险、生命、反弹、死亡和重大剧情；
- 不新增紫蓝霓虹或多色渐变作为主视觉。

### 9.2 使用纪律

- 场景美术决定大面积颜色，UI 色只负责信息层级。
- 语义强调色在单个视口内应保持克制，不能覆盖大面积背景。
- 明暗主题保持同一锚色，只改变明度与饱和度。
- 正文目标对比度 `7:1`，最低不低于 `4.5:1`。
- 焦点环和控件边界最低 `3:1`，不能只依靠颜色表示状态。

## 10. 立绘与构图合同

### 10.1 站位

标准站位为：

- `left`：舞台中心线左侧；
- `center`：舞台中心；
- `right`：舞台中心线右侧。

允许临时使用 `far-left` 和 `far-right` 表达旁观者，但同屏角色仍不得超过五名；普通对白场景建议不超过三名。

### 10.2 尺寸

- 半身或膝上立绘高度建议占舞台 `72%–92%`。
- 当前说话者保持正常亮度与对比度。
- 非说话者只降低少量亮度，不能暗到无法辨认表情。
- 人物眼睛一般落在舞台高度 `24%–38%` 区域，避免被对话框遮挡。
- 表情切换必须保持人物锚点不变，禁止角色产生跳位。

### 10.3 主角

主角采用第一人称叙事，标准剧情中不显示正面立绘。需要表现主角动作时优先使用手部、武器、剪影、第一视角 CG 或屏幕特效。

## 11. 动效与转场

### 11.1 允许的核心动效

整套游戏常规动效限制为三类：

1. 背景与场景淡入淡出；
2. 角色入退场与表情交叉淡化；
3. 战斗和重大剧情的一次性受击反馈。

默认只动画 `opacity` 与 `transform`。禁止通过动画改变布局高度、边距、定位或正文容器尺寸。

### 11.2 时长

| 类型 | 建议时长 |
| --- | ---: |
| 按钮按下与状态反馈 | `100–150ms` |
| 表情切换 | `150–220ms` |
| 人物入退场 | `220–300ms` |
| 背景切换 | `360–500ms` |
| 模态覆盖层 | `220–420ms` |
| 受击闪烁／震动 | `100–240ms` |

进入使用 `--ease-out`，离开使用 `--ease-in`，状态切换使用 `--ease-in-out`。不使用弹跳、回弹、视差、自定义鼠标和无意义无限循环。

### 11.3 减少动态效果

当系统或游戏设置启用减少动态效果时：

- 空间位移动画改为不超过 `150ms` 的透明度切换；
- 关闭震屏和装饰粒子；
- 保留必要的加载、战斗结果和状态反馈。

## 12. 输入合同

### 12.1 鼠标

| 操作 | 行为 |
| --- | --- |
| 左键单击舞台／对白框 | 显示完整当前页或推进 |
| 右键 | 隐藏／恢复对话框与快捷菜单 |
| 滚轮向上 | 打开历史记录 |
| 滚轮向下 | 历史关闭时推进一页，可在设置中关闭 |

### 12.2 键盘

| 按键 | 行为 |
| --- | --- |
| `Enter`／`Space` | 显示完整当前页或推进 |
| 按住 `Ctrl` | 快进 |
| `A` | 开关自动播放 |
| `B` | 打开历史记录 |
| `H` | 隐藏／恢复界面 |
| `Q` | 快速保存 |
| `L` | 快速读取 |
| `Esc` | 打开／关闭游戏菜单 |

输入框、滑块、下拉菜单或模态窗口拥有焦点时，剧情快捷键必须停用。所有鼠标操作必须有键盘等价方式，焦点环必须清晰可见。

### 12.3 自动与快进

- 自动播放只在文字全部显示后开始计时。
- 自动等待时间根据文本长度与设置计算，并设最低停留时间。
- 进入选项、菜单、历史、存读档或战斗输入时自动暂停。
- 快进可以连续跳过已读与未读文本，并在选项、战斗和覆盖层处暂停。
- 自动和快进状态必须在快捷菜单中有持续但克制的可见反馈。

## 13. 控件状态与文案

每个交互控件必须考虑以下状态：

```text
default · hover · focus-visible · active · disabled · loading · error · success
```

- 不支持的状态可以复用基础外观，但不能导致布局变化。
- 成功操作优先静默反馈，例如存档位更新时间变化；不滥用庆祝动画或 Toast。
- 错误信息必须说明发生了什么以及玩家下一步能做什么。
- 按钮使用简短动词：“保存”“读取”“返回”“继续”，不写成说明句。
- 可点击标签在桌面和小屏都应保持单行；容器重排，而不是让按钮文字换行。

## 14. 音频合同

虽然美术和声音不属于第一阶段重点，接口从一开始就必须预留：

- BGM、环境音、音效和语音是独立通道；
- 每个通道可单独调节，提供总静音；
- 浏览器获得首次用户交互后才开始播放；
- 场景切换时 BGM 可淡出、保持或替换，由剧情事件明确指定；
- 打开菜单不停止 BGM，但可降低音量；
- 暂无语音资源时，语音事件可以为空，不能阻塞文本推进。

## 17. AI Agent 修改协议

后续任何 Agent 开始视觉小说相关改动前，必须先阅读：

1. `AGENTS.md`；
2. 本文；
3. `docs/AI-AGENT-STORY-GUIDE.md`；
4. 与任务相关的现有组件、样式、剧情或测试。

### 17.1 修改界面时

- 优先新增语义组件或扩展现有组件，不把整个游戏继续堆进单一 TSX 文件。
- 复用 `tokens.css`，颜色、字体、间距、层级和动效不得在组件中随意写死。
- `app/globals.css` 只做渐进式整理；在得到明确授权前不得删除大段既有样式。
- 每一个新控件都检查键盘操作、焦点、禁用、加载、错误和成功状态。
- 所有基线尺寸至少检查 `1280 × 720`、`1366 × 768`、`1440 × 900` 和 `1920 × 1080`。
- 紧凑布局至少检查 `320`、`375`、`414`、`768` 像素宽度。

### 17.2 修改剧情时

- 只改剧情数据，不在视觉组件中增加角色专属条件。
- 不改变五幕节点数量，除非用户明确授权。
- 一段文字装不下时增加视觉小说事件或分页，不增加剧情节点。
- 新资源先登记资源键，再在剧情事件中引用。

### 17.3 修改战斗时

- 数值结算只能改 `lib/xue-gu-yin/combat.ts` 及相关测试。
- 战斗表现层不得自行计算伤害、真元、治疗、反弹或胜负。
- 新增视觉反馈时消费共享结算结果，不复制规则。
- 每个蛊术选项同时显示作用说明与真元消耗；真元不足时仍显示所需值，调息则显示恢复量。
- 敌人被击败后先短暂晃动再淡出；启用减少动态效果时改为 150ms 淡出。
- 玩家被击败后显示敌人专属落败文本，随后进入场景声明的死亡结局，不再由同伴救场。

### 17.4 每次提交前

```powershell
pnpm lint
pnpm test
pnpm build
```

三项必须通过。涉及视觉改动时还需完成目标视口的截图或浏览器人工检查。
